# Сервис моделирования трасс подключения к тепловым сетям

По входному GeoJSON района сервис строит новую тепловую сеть, подбирает диаметры,
считает стоимость и выдаёт до трёх содержательно разных вариантов с рангом — в плане и, дополнительно,
с профилем глубины.

Описание решения: **[docs/solution.md](docs/solution.md)**.
Готовый результат на наборе: **[data/results/final/](data/results/final/)**.

## Результат на конкурсном наборе

| | |
|---|---|
| score лучшего варианта | **11.7016** (меньше — лучше) |
| Длина новой сети | **1 673 м**, стоимость строительства **238.7 млн ₽** |
| Точек подключено | **17 из 17**, штрафов за неподключение нет |
| Ошибок независимого валидатора правил | **0** |
| Время полного расчёта всех вариантов | **20 с** |

Лучший вариант: 26 участков ДУ65…ДУ300, 12 новых камер на разветвлениях (50 млн ₽), врезок в
существующие камеры не потребовалось. Ещё два варианта — score 11.9646 и 11.9898.

## В решении:

**Выдачу проверяет независимый валидатор правил.** Отдельная реализация всех правил Техприложения
читает готовый GeoJSON и проверяет каждый участок: отступы, углы поворота, границы спецпроходов и
Kспец, расходы и ДУ, предельную длину, стоимость, глубину и вертикальные просветы. Отчёт лежит рядом
с результатом, доступен по API и виден прямо в `variant_summary` (`validation_errors`,
`validation_warnings`). На конкурсном наборе, всей синтетике, четырёх районах Москвы и фаззинг-корпусах
— **0 ошибок**.

**Результат воспроизводим побайтно.** Бюджет перебора задан в проверках отрезков, а не в секундах: на
1, 2, 4 и 16 потоках получается один и тот же score. Выдача сервиса, поднятого через
`docker compose up` на чистом окружении, совпадает с файлом в репозитории побайтно — и в плане, и с
глубиной.

**Общие магистрали вместо отдельной трассы на каждую точку.** Та же программа с ключом
`-Dstrategies=naive` подключает каждую точку отдельно: 6 995 м, 851 млн ₽, две точки вообще не
дотягиваются. Объединение в дерево с общими участками даёт 1 673 м и 239 млн ₽ — **в 4.3 раза лучше
по score**. Цена объединения считается честно: рост ДУ магистрали и стоимость камеры разветвления,
а не геометрическая длина.

**Правила — данные, а не код.** Отступы, коэффициенты спецпроходов, условия пересечения и вертикальные
просветы вынесены в профили `src/main/resources/profiles/*.yml`. Те же наборы проходят под профилями
водоснабжения и кабелей: меняются отступы и коэффициенты, трассировка не ломается.

**Спорные трактовки помечены, а не спрятаны.** Там, где ТЗ допускает два чтения, выбор пишется в
выдачу (`approach` у участка) и в отчёт валидатора как WARNING. Проверяющий видит, где решение приняло
трактовку за организаторов.

## Запуск

```bash
docker-compose up --build -d
```

Поднимаются приложение и PostgreSQL с PostGIS; миграции Flyway применяются автоматически. Проверено на
чистой Ubuntu 22.04.5 со штатным `docker-compose 1.29.2`; `docker compose` версии 2 тоже работает.
Сборка требует сети для образов и зависимостей Maven; работа собранного приложения полностью офлайн.

| | |
|---|---|
| Интерфейс | <http://localhost:8080/> |
| Swagger | <http://localhost:8080/swagger-ui.html>, схема `/v3/api-docs` |
| Готовность | <http://localhost:8080/actuator/health> |

## Проверить за 5 минут

```bash
JOB_ID=$(curl -fsS -F file=@data/samples/dataset.geojson -F mode=PLAN_2D http://localhost:8080/api/v1/jobs | sed -E 's/.*"jobId":"([^"]+)".*/\1/')
curl -fsS "http://localhost:8080/api/v1/jobs/$JOB_ID"
curl -f   "http://localhost:8080/api/v1/jobs/$JOB_ID/result" -o result.geojson
curl -fsS "http://localhost:8080/api/v1/jobs/$JOB_ID/validation" | head -20
```

Последняя команда печатает отчёт независимого валидатора: `errorCount: 0`. Тот же результат уже лежит
в `data/results/final/` — выдача сервиса совпадает с ним побайтно.

Посмотреть глазами: <http://localhost:8080/> — загрузить только исходный GeoJSON, запустить расчёт и
увидеть вход, результат, сравнение вариантов и отчёт валидатора на одной странице. Leaflet включён в
образ, тайлы и внешние API не используются; предпросмотр входа в браузере ограничен 50 МБ, файлы крупнее
всё равно считаются через API. Резервный автономный просмотрщик готовых файлов — `tools/viewer.html`.

## HTTP-контракт

| Метод | Путь | Результат |
|---|---|---|
| POST | `/api/v1/jobs` | multipart `file`, `mode=PLAN_2D`\|`DEPTH_3D`; 202 `{jobId, connectionPoints, estimatedSeconds}` |
| GET | `/api/v1/jobs/{id}` | статус, режим, времена, размер входа, диагностика |
| GET | `/api/v1/jobs?page=0&size=20&status=DONE` | список заданий, фильтр по статусу |
| DELETE | `/api/v1/jobs/{id}` | отмена `UPLOADED`/`RUNNING`, итоговый статус `CANCELLED` |
| GET | `/api/v1/jobs/{id}/result` | `application/geo+json` |
| GET | `/api/v1/jobs/{id}/validation` | отчёт независимого валидатора по сохранённому GeoJSON |

Коды: 422 — диагностика входа по объектам; 400 — параметры; 404 — неизвестное задание; 409 — результат
не готов; 413 — загрузка сверх 3 ГиБ; 503 — очередь заполнена.
Необязательные параметры загрузки: `resource=heat|water|cable`, `pin_tie_in`, `exclude_tie_in`,
`exclude_restriction`.

## Стек

Java 11, Spring Boot 2.6.3, Spring Data JPA, PostgreSQL 16 с PostGIS, Flyway V1–V3,
springdoc-openapi-ui 1.7.0, JTS, proj4j, Jackson streaming, docker-compose. Внешних вызовов нет.

## Что в репозитории

```
src/main/java/ru/lct/heat/
  api/         REST, очередь заданий, асинхронный расчёт
  io/          потоковый разбор GeoJSON, запись результата, CRS 4326↔32637, CLI
  model/       входные сущности и справочники (таблицы ДУ, ограничений, камер)
  geometry/    JTS: зоны отступа, спецзоны, углы, пространственные индексы
  routing/     карты препятствий, A* по графу видимости, дерево, ремонт, спецучастки
  sizing/      расходы по дереву, подбор ДУ, предельная длина
  cost/        стоимость участков, камер, врезок, штрафов, score и ранжирование
  variants/    генерация и отбор содержательно разных вариантов
  depth/       режим с профилем глубины
  validation/  диагностика входа и независимый валидатор выдачи
  persistence/ Spring Data JPA: задания и результаты
data/samples/    конкурсный датасет
data/synthetic/  синтетика и четыре района Москвы из OpenStreetMap
data/results/    итоговая выгрузка и отчёты валидатора
docs/spec/       первоисточники: Техприложение, описание кейса, разъяснения
tools/           офлайн-просмотрщик и smoke-тест API
scripts/         генераторы наборов и построение иллюстраций
```
